**One new function — place a subtitle beside its video, untouched — and a safer way of writing every file.**

Nothing about pairing or retiming changed.

---

## `place_subtitle()` — a subtitle file beside its video, byte for byte

[hato](https://github.com/SonicSandbox/hato) gained an opt-in choice for a video with no
subtitles inside it: download one chosen by its name and put it beside the video, *not
timed* — there is nothing inside such a video to time it against. hato's rule is that the
only writes in a media folder are tsubasa's, so tsubasa places it.

```python
import tsubasa

got = tsubasa.place_subtitle("Show - 01.mkv", "downloads/[Group] Show - 01.ja.ass",
                             write=True)
if not got.ok:
    print("not placed:", got.reason)
elif got.write_failed:
    print("checked, but not written:", got.reason)
else:
    print("placed as", got.output_path)             # Show - 01.ja.ass
```

- **Untouched.** The bytes written are the bytes read — never converted, never re-encoded,
  never timed.
- **Named by tsubasa's own rule**, `<video>.<language>.<ext>`, the language read from the
  subtitle's name. A name that gives no language is refused: written untagged, it would read
  as no subtitle at all.
- **`lang_tag`** writes the language code exactly as given, when it means the subtitle's own
  language: `lang_tag="jpn"` places `Show - 01.jpn.ass`. hato uses `.jpn.` to mark a file
  nobody timed; players read it as Japanese, like `.ja.`.
- **Never over a file that is already there** — beside the video or in `out_dir`. Without
  `write=True` it checks everything, writes nothing, and says the name it would write
  (`target`) — so a caller can decide before anything lands.
- **Refused with a reason:** an empty file, one over 16 MB, an extension that is not a
  subtitle's (`srt`, `ass`, `ssa`, `vtt`).

## A safer way of writing a file — for `place_subtitle` and `extract_subtitle` alike

- **A folder that refuses new files no longer hangs.** On Windows, writing into a folder that
  denies creating a file could retry temporary names for days. It now fails at once, and
  says why.
- **A file that appears while tsubasa writes is not overwritten.** The new file is published
  in one step that refuses a name already taken; before, a file landing between the check
  and the write could be replaced. On a drive with no hard links (exFAT, a network share)
  the name is reserved first, then filled.
- **Long Japanese names are no longer cut short on Windows.** The 255 limit is counted the
  way the file system counts it — UTF-16 units on Windows, bytes elsewhere. A video named in
  91 kanji had its subtitle's name cut to 82 characters, which no player then paired with it.
- **Readable by everyone who may read the folder.** On Linux and macOS every file tsubasa
  wrote was readable only by its owner — a media server running as another user could not
  load the subtitle. New files now get the usual permissions.
- **Smaller fixes:** a leftover temporary file is reported, never hidden behind the real
  error; `CONIN$`, `CONOUT$` and the superscript `COM¹`–`LPT³` device names are disarmed like
  the others; a Hindi subtitle (`.hi.`) beside a name that ends in a word like `Be` reads back
  as Hindi; a folder given as `out_dir` that is really a file is said in those words.

## Getting it

**The app, no Python needed:** download `tsubasa-windows-x64.zip` below, unzip
it anywhere, double-click `tsubasa-gui.exe`. `SHA256SUMS` is the checksum.

> ⚠ Unsigned, so the first launch shows *"Windows protected your PC"* — click
> **More info**, then **Run anyway**.

**As a command or a library:**

```
pip install --upgrade tsubasa-sync
```

```
tsubasa /path/to/your/folder
```

**ffmpeg is not bundled.** Matroska files with a subtitle track inside need
nothing; any other container needs `ffmpeg` and `ffprobe` on `PATH`, or the
folder holding them in `TSUBASA_FFMPEG`.
